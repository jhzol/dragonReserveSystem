# 天气获取优化技术实施方案

> 用途：直接交给 5.6 Terra 执行。
> 基线日期：2026-09-03。
> 当前分支：`feat/board-game-library-20260831`。
> 本方案只定义实施，不代表允许部署、合并、提交 Git 或覆盖当前未提交修改。

## 1. 结论

采用“**服务端持久化天气快照 + 定时刷新 + 活动详情直接下发 + 小程序轻量本地缓存**”的混合方案。

核心原则：

1. 用户每次进入活动详情页时，不再同步调用和风天气。
2. 天气结果由服务端提前刷新并持久化，一条活动绑定一条目标日期天气快照。
3. 同一地点的多个活动在一次刷新任务中合并请求：30 日天气只请求一次，再按各活动日期拆分写入。
4. 活动详情接口直接返回已保存的天气数据，小程序不再额外调用公开天气接口。
5. 小程序本地缓存只用于减少重复渲染和短暂闪烁，不作为天气事实来源。
6. 和风天气失败时保留有限时间内的最后一次成功结果，不阻塞活动详情接口。
7. 现有旧版本小程序使用的 `/weather/activity` 暂时保留兼容，但只能读服务端快照，不能触发外部天气请求。

该方案同时解决：外部 API 被页面访问频率放大、服务重启后缓存清空、并发缓存穿透、同一地点重复拉取、详情页天气加载闪烁和公开接口可被滥用的问题。

## 2. 当前实现与已确认问题

### 2.1 当前调用链

当前代码链路：

```text
活动详情页 applyActivity
  → loadWeather(activity)
  → miniprogram/services/weather.js
  → GET /api/v1/weather/activity?longitude=&latitude=&date=
  → QWeatherService.get_activity_weather()
  → /v7/weather/30d
  → /airquality/v1/daily/{lat}/{lng}
```

代码依据：

- `miniprogram/pages/activity_detail/activity_detail.js`
- `miniprogram/services/weather.js`
- `backend/app/api/v1/weather.py`
- `backend/app/services/qweather_service.py`

### 2.2 当前已有缓存

后端已有 30 分钟进程内缓存：

```text
QWEATHER_CACHE_SECONDS=1800
cache key = 经度四位小数 + 纬度四位小数 + 活动日期
```

它只能减少单个后端进程存活期间的重复请求，不是持久化缓存。

### 2.3 根因清单

1. `applyActivity()` 每次执行都会重置天气为“加载中”并调用 `loadWeather()`。
2. 首次进入、页面重新显示、报名/签到等操作后的详情刷新，都可能再次走天气接口。
3. `/weather/activity` 是按经纬度和日期直接查询的公开接口；任意请求在缓存未命中时都能触发外部 API。
4. 当前缓存保存在 Python 内存中，后端重启或重新部署后立即清空。
5. 当前缓存没有并发请求合并；同一 key 同时失效时，多个请求可能一起访问和风天气。
6. 缓存 key 包含活动日期，但 `/v7/weather/30d` 一次已经返回同一地点的多日数据；同地点不同日期仍会重复拉取完整 30 日数据。
7. 天气和空气质量请求位于详情请求链路中，外部网络延迟会直接增加天气卡片等待时间。
8. 当前接口异常全部降级为统一不可用，缺少可观测的刷新状态、失败次数和最后成功时间。
9. 小程序没有天气本地缓存，重复执行 `applyActivity()` 时会出现不必要的“天气加载中”闪烁。

## 3. 方案比较

| 方案 | 能否降低单设备请求 | 能否保护外部 API | 重启后保留 | 多设备共享 | 推荐结论 |
|---|---:|---:|---:|---:|---|
| 只做小程序本地缓存 | 是 | 否 | 仅客户端保留 | 否 | 不采用为主方案 |
| 只增强服务端内存缓存 | 是 | 部分 | 否 | 单进程内共享 | 不采用为主方案 |
| 页面请求时服务端查库，过期再同步刷新 | 是 | 部分 | 是 | 是 | 页面仍受外部 API 延迟影响 |
| 每个活动单独定时请求并保存 | 是 | 是 | 是 | 是 | 同地点活动会重复请求 |
| **活动快照 + 按地点合并定时刷新** | **是** | **是** | **是** | **是** | **本次采用** |

不引入 Redis、Celery、消息队列或第三方缓存服务。当前项目是单机 FastAPI + MySQL + systemd，使用数据库和 systemd timer 足够，避免增加无必要的基础设施。

## 5. 业务规则

### 5.1 可刷新活动

同时满足以下条件才允许进入刷新候选：

1. 活动存在有效经纬度。
2. 活动未删除、未取消、未结束。
3. 活动尚未超过结束时间；当天已经开始但仍在进行的活动仍可刷新。
4. 活动日期已经进入当前天气接口能够覆盖的预报范围。

没有定位：保存或返回 `location_unavailable`，不访问和风天气。

超出预报范围：保存 `forecast_out_of_range`，不访问和风天气；`next_refresh_at` 直接设置为活动进入预报范围的时间，而不是周期性空请求。

活动结束、取消或删除后停止刷新。为接近当前页面语义，活动结束后的当天可继续展示最后一次成功快照；目标日期过去后返回超出范围状态，不长期展示历史预报。

### 5.2 活动与快照绑定

- 每个活动最多一条 `ActivityWeatherSnapshot`。
- 快照目标日期取活动开始时间在项目业务时区下的自然日。
- 快照记录生成时使用的经纬度和地点 key。
- 活动开始时间、纬度或经度发生变化时，原快照立即失效并进入待刷新状态。
- 仅修改标题、备注、人数等字段时，不失效天气快照。

### 5.3 服务端是事实来源

- 服务端数据库快照是唯一事实来源。
- 小程序本地缓存只能展示服务端曾经下发过的结果。
- 小程序不得自行延长服务端给出的有效期。
- 服务端返回明确的不可用状态时，该状态优先于本地旧数据。

索引：

```text
PRIMARY KEY(activity_id)
INDEX ix_activity_weather_next_refresh_at(next_refresh_at)
INDEX ix_activity_weather_location_key(location_key)
INDEX ix_activity_weather_status(status)
```

不保存 JWT、私钥内容、Authorization 请求头和完整上游响应。

### 6.2 地点 key

统一函数：

```python
def build_weather_location_key(longitude: float, latitude: float) -> str:
    return f"{longitude:.4f}:{latitude:.4f}"
```

所有刷新、分组、失效判断和旧接口兼容都必须复用同一个函数，禁止在不同文件中各自拼接。

四位小数与当前缓存精度一致，约为十米级；对于天气预报足够，同时可合并同一场馆的轻微坐标差异。

## 7. 后端响应结构

### 7.1 新增 Schema

在 `backend/app/schemas/activity.py` 增加：

```python
class ActivityWeatherResponse(BaseModel):
    available: bool
    status: str
    reason: str | None = None
    date: date | None = None
    temperature: int | float | None = None
    temperature_min: int | float | None = None
    temperature_max: int | float | None = None
    condition: str = ""
    icon_code: str = ""
    humidity: int | float | None = None
    wind_direction: str = ""
    wind_scale: str = ""
    air_quality: str | None = None
    attribution: str
    fetched_at: datetime | None = None
    valid_until: datetime | None = None
    stale: bool = False
```

新增详情专用响应：

```python
class ActivityDetailResponse(ActivityResponse):
    weather: ActivityWeatherResponse
```

列表接口继续使用现有 `ActivityResponse`，不把天气数据加入首页、日程、排行榜等无关响应。

### 7.2 活动详情接口

`GET /activities/{activity_id}` 改为返回 `ActivityDetailResponse`。

请求处理只允许：

1. 查询活动。
2. 查询其天气快照。
3. 根据有效期组装响应。

请求处理禁止：

- 同步访问和风天气。
- 生成 JWT 后发起外部 HTTP 请求。
- 因天气失败让活动详情接口报错。

没有快照时返回稳定不可用结构，不返回 `null`，避免前端增加多套分支：

```json
{
  "available": false,
  "status": "pending",
  "reason": "weather_pending",
  "attribution": "天气服务驱动 by QWeather",
  "stale": false
}
```

### 7.3 旧接口兼容

暂时保留：

```text
GET /weather/activity?longitude=&latitude=&date=
```

改造后该接口只能：

1. 标准化经纬度为 `location_key`。
2. 从 `activity_weather_snapshots` 中寻找相同地点和目标日期的最新有效快照。
3. 返回与旧版一致的天气结构。
4. 找不到时返回 `available=false`。

该接口不得再调用 `QWeatherService`，从而保证旧版本小程序也不能通过页面访问频率放大外部 API。保留至少一个小程序发布周期，后续是否删除另行决定。

## 8. 和风天气客户端重构

### 8.1 职责拆分

将当前 `QWeatherService.get_activity_weather()` 拆为：

```text
QWeatherClient
  - 负责 JWT、HTTP、状态码和原始响应

QWeatherParser
  - 负责按日期提取天气和空气质量并标准化

ActivityWeatherRefreshService
  - 负责候选活动、地点分组、快照更新、退避和日志
```

建议文件：

```text
backend/app/services/qweather_client.py
backend/app/services/qweather_parser.py
backend/app/services/activity_weather_service.py
```

可保留 `qweather_service.py` 作为兼容入口，但不得继续承载请求级内存缓存和活动详情同步拉取。

### 8.2 HTTP 与 JWT

- 使用一个可复用的 `httpx.Client`，启用连接池；不要每次调用顶层 `httpx.get()` 新建连接。
- 总超时沿用 `QWEATHER_TIMEOUT_SECONDS`，定时任务内单次请求失败后按刷新策略退避。
- JWT 可缓存在进程内，到期前 60 秒重新生成；JWT 只用于服务端到和风天气的请求。
- 日志禁止输出 JWT、私钥、完整 Authorization 头和凭证 ID 组合。
- 天气接口失败和空气质量接口失败分开处理；空气质量失败不能清空成功的天气数据。

### 8.3 一次请求，多活动复用

刷新任务先按 `location_key` 对活动分组。

每个地点组：

1. `/v7/weather/30d` 最多请求一次。
2. 将返回的多日预报按日期建立字典。
3. 对该地点下所有活动，根据各自 `target_date` 提取对应一天的数据。
4. 只有组内存在进入空气质量预报范围的活动时，才请求一次空气质量日预报。
5. 将同一份上游响应拆分写入多条活动快照。

禁止按“每个活动一次 30 日请求”的方式实现。

### 8.4 保持现有数据语义

沿用当前字段选择：

- 主温度：优先 `tempMax`，缺失时取 `tempMin`。
- 天气文案：优先白天，缺失时取夜间。
- 图标：优先白天，缺失时取夜间。
- 湿度：沿用日预报 `humidity`。
- 风向、风力：优先白天，缺失时取夜间。
- 空气质量：优先中国环境监测总站口径索引，沿用当前 `cn-mee-1h / cn-mee` 选择逻辑。
- 归因文案：保持当前页面实际文案，不在本轮改视觉。

## 9. 刷新策略

### 9.1 timer 频率

新增：

```text
backend/deploy/dragonreserve-weather-refresh.service
backend/deploy/dragonreserve-weather-refresh.timer
backend/scripts/refresh_activity_weather.py
```

systemd timer 每 1 小时运行一次，只检查 `next_refresh_at`，不代表每小时都会请求一次和风天气：

```text
OnBootSec=2min
OnUnitActiveSec=1h
Persistent=true
RandomizedDelaySec=60
```

任务使用 oneshot，复用项目现有活动状态同步 timer 的部署方式。

### 9.2 动态刷新间隔

| 距活动开始 | 天气刷新间隔 | 空气质量刷新 |
|---|---:|---:|
| 尚未进入预报范围 | 不请求；到进入范围时再检查 | 不请求 |
| 8～29 天 | 12 小时 | 不请求 |
| 3～7 天 | 6 小时 | 不请求 |
| 0～2 天 | 6 小时 | 3 小时 |
| 活动已开始但未结束 | 3 小时 | 3 小时 |
| 活动已结束/取消/删除 | 停止 | 停止 |

说明：现有天气接口返回多日预报，而空气质量日预报覆盖范围更短。任务必须先判断目标日期是否处于对应接口范围，不能靠请求后发现无数据。

天气刷新行为参数做成配置，便于以后调整：

```text
QWEATHER_REFRESH_FAR_HOURS=12
QWEATHER_REFRESH_NEAR_HOURS=6
QWEATHER_AIR_REFRESH_NEAR_HOURS=3
QWEATHER_STALE_MAX_HOURS=24
QWEATHER_REFRESH_BATCH_SIZE=100
QWEATHER_REFRESH_MAX_CONCURRENCY=2
```

实际额度以和风天气账户控制台为准，代码不硬编码套餐额度。

### 9.3 创建和编辑后的刷新

活动创建后：

1. 同事务创建 `pending` 快照。
2. 设置 `next_refresh_at=now`；超出预报范围时设置为进入范围的时间。
3. 接口正常返回，不等待外部天气请求。

活动编辑时，仅在以下任一字段变化后失效：

- `start_time`
- `location_latitude`
- `location_longitude`

失效后更新目标日期、地点 key 和源经纬度，清空不再匹配的新旧天气字段，重新设置 `next_refresh_at`。

可在创建/编辑路由中通过 FastAPI `BackgroundTasks` 发起一次内部 best-effort 刷新，以缩短首次出现天气的等待；该任务必须在数据库提交后使用独立 Session 执行，失败后仍由 systemd timer 补偿。不得让创建/编辑接口等待和风天气返回。

### 9.4 失败与陈旧数据

刷新失败时：

- 如果存在距现在不超过 24 小时的最后成功结果：保留原天气字段，响应标记 `stale=true`，不让页面突然变成空白。
- 如果没有可用旧结果：状态改为 `upstream_unavailable`，页面沿用当前不可用状态。
- 连续失败次数递增，不覆盖 `last_success_at`。
- 成功后 `failure_count` 清零，`stale=false`。

建议退避：

| 连续失败次数 | 下次重试 |
|---:|---:|
| 1 | 15 分钟后 |
| 2 | 1 小时后 |
| ≥3 | 3 小时后 |

不得在一次 timer 执行中无限重试。

### 9.5 防重入和并发

- 同一个 systemd oneshot service 自身不得重叠执行。
- 脚本启动时增加全局刷新锁；推荐 MySQL advisory lock 或部署层 `flock`，二选一即可，不同时叠加。
- 地点组之间最大并发为 2，默认可先串行实现；禁止高并发批量请求。
- 每个地点组独立提交，单个地点失败不能回滚其他地点的成功结果。

### 10.2 本地缓存

新增：

```text
miniprogram/utils/activityWeatherCache.js
```

缓存 key 必须包含环境和活动维度：

```text
activityWeather:{apiBaseUrlSignature}:{activityId}
```

缓存内容：

```js
{
  activityId,
  targetDate,
  locationKey,
  weather,
  fetchedAt,
  validUntil,

```

读取规则：

1. 必须在活动详情已经返回、能够计算目标日期和地点 key 后读取。
2. `activityId + targetDate + locationKey` 必须全部匹配。
3. 当前时间不得超过服务端 `validUntil`。
4. 服务端返回更新结果时，以服务端为准并覆盖本地缓存。
5. 服务端返回明确不可用状态时，清理该活动旧的可用缓存，不能继续展示错误地点或错误日期的天气。
6. 正式环境和测试环境通过 API base URL 命名空间隔离。

缓存只用于避免同一个页面数据重新适配时闪回“加载中”，不额外延长天气有效期。

清理规则：

- 最多保留 30 条活动天气缓存。
- 删除超过 7 天未访问的条目。
- 活动日期或位置改变后覆盖旧条目。
- 复用项目 `_safeGet / _safeSet` 风格，存储异常不能影响页面。

### 10.3 展示状态

保持现有视觉，仅统一数据状态：

| 服务端状态 | 页面表现 |
|---|---|
| `available` | 展示天气、温度、湿度、风向风速、空气质量和归因 |
| `pending` | 沿用当前加载/暂不可用表现，不新增文案 |
| `forecast_out_of_range` | “距离活动时间较远，暂不展示天气信息” |
| `location_unavailable` | 沿用原型中的无定位天气状态 |
| `upstream_unavailable` 且无旧数据 | 沿用天气不可用状态 |
| `available` 且 `stale=true` | 继续展示最后成功数据，不新增“已过期”等原型外文案 |

本轮不新增用户可见文字，不改变原型。

## 12. 后端测试计划

至少覆盖：

1. 活动详情只读取数据库快照，调用过程不会访问和风天气。
2. 没有快照时返回稳定 `pending` 结构。
3. 有效快照正确映射为详情 `weather`。
4. 过期但在 stale 上限内的成功快照继续返回且 `stale=true`。
5. 超过 stale 上限后不展示旧结果。
6. 无定位活动不请求上游并写入 `location_unavailable`。
7. 超出预报范围不请求上游，`next_refresh_at` 计算正确。
8. 两个同地点、不同日期的活动只调用一次 30 日天气接口，并分别保存对应日期数据。
9. 同地点多个近日期活动只调用一次空气质量接口。
10. 天气成功、空气质量失败时仍保存天气字段，空气质量为空。
11. 创建活动生成正确的 pending 快照。
12. 修改日期或经纬度会失效快照。

14. 活动结束、取消、删除后不再刷新；删除活动时快照级联删除。
15. 连续失败退避时间正确，成功后失败次数清零。
16. 旧 `/weather/activity` 只读取快照，不访问和风天气。
17. 并发或重复任务不会为同一地点产生重复上游请求。
18. JWT 缓存到期刷新，日志不含 token 和私钥内容。
19. 数据库迁移升级、回滚语法有效。
20. timer 脚本无候选活动时正常退出并返回 0。

## 14. 可观测性

每次刷新任务输出一条结构化汇总日志：

```text
weather_refresh_summary
candidate_activity_count
unique_location_count
weather_request_count
air_request_count
snapshot_success_count
snapshot_unavailable_count
snapshot_stale_count

```

每个失败地点只记录：

```text
location_key
error_type
upstream_status_or_code
failure_count
next_refresh_at
```

禁止记录：

- JWT
- 私钥内容或完整私钥路径
- Authorization 头
- 完整上游响应
- 和风天气凭证组合

活动详情接口可在内部日志记录天气来源：`snapshot / stale_snapshot / unavailable`，但不得记录每次完整天气对象。

## 18. 回滚策略

- 小程序回滚：旧前端继续使用 `/weather/activity`，新后端兼容接口从快照读取，不触发外部 API。
- timer 回滚：停止并禁用 weather timer；已有快照保留，详情按有效期或 stale 规则展示。
- 后端代码回滚：保留新增表不会影响旧代码；不要在紧急回滚中立即执行 downgrade 删除天气快照。
- 上游异常：禁用 timer 后活动详情仍可正常使用，天气按旧快照或不可用状态降级。
- 快照数据异常：可只清理 `activity_weather_snapshots` 后重新 warmup，不影响活动、报名和签到数据；任何清理操作执行前必须另行取得用户确认。

## 20. 完成定义

同时满足以下条件才算完成：

- 页面访问不再直接或间接触发和风天气请求。
- 天气快照持久化并与活动日期、地点正确绑定。
- 同地点活动能够合并上游请求。
- 创建或编辑活动后快照能够正确失效并重新生成。

- 外部 API 失败不影响活动详情、报名和签到。

- 所有测试和 L1 验收通过。
- 天气组件视觉未发生本轮范围外变化。
- 凭证、JWT、私钥和完整上游响应未进入仓库或日志。
- 没有覆盖当前未提交修改，没有擅自部署、合并、提交或删除文件。
